# ConfastDB: Phase 1 Authorization Audit and Permission Inventory

Audit date: October 9, 2026. This is a planning report, not an RBAC implementation.

## 1. Executive Summary

**Confirmed:** ConfastDB uses ASP.NET Core Identity with PostgreSQL persistence, cookie authentication, Blazor Interactive Server circuits, and four seeded roles: `Administrator`, `Quality`, `Production`, and `ReadOnly`. Multiple direct roles already work. There is no implemented configurable permission catalog, role inheritance, permission policy provider, or centralized application authorization service.

Authorization is uneven. Container tracking, receiving, scheduling, production tracking, production review, chat, profile pictures, and presence have database-backed service checks. Customer, part, gage, inspection-criteria, inspection, and certification services generally have no caller authorization. Several administrative services depend on an administrator-authorized page. Those pages are real server-side route gates; they are not merely hidden links. Nevertheless, their public services do not independently protect privileged operations or recheck current privileges during an existing circuit.

The most consequential compatibility issue is that **`ReadOnly` is a role name, not a global restriction**. An authenticated user with only that role, or no roles, can use ordinary writable customer, part, criteria, gage, and inspection pages. A strict read-only seed would change current behavior; granting the old broad access would preserve a misleading and possibly unintended arrangement. This needs a deliberate decision, not an accidental migration.

Chat largely enforces membership in trusted code, including history, attachments, inbox, polls, reactions, and scheduled delivery. Administrator channel-management privileges do not imply private conversation reading or private-member management. Preserve that distinction.

### Scope, evidence, and limitations

- Repository HEAD at audit start: `9351caf5fa0b28d38f703fa746093d4caba3158c`. Findings describe the **current working tree**, including the pre-existing chat changes and `20261009121947_AddHiddenDirectConversations` migration, rather than HEAD alone.
- Searched application and tests for attributes, policies, role names, identity/claims, guard calls, authorization exceptions, ownership/membership filters, UI conditions, endpoint mapping, hosted services, and environment switches. Reviewed all implemented feature directories and the read/write method inventory below. Checked project JavaScript separately, excluding vendored libraries from application findings.
- **Confirmed** means supported by source. **Requires Verification** means exploitability, active-circuit behavior, production deployment state, or a concurrency scenario has not been established by runtime evidence. **Recommendation** means a future design choice, not present functionality.
- No database queries, live role/account enumeration, authenticated browser tests, SMTP sends, builds, or test runs were performed. The installed database may contain extra roles or externally managed claims not visible in source. Production key-ring configuration and actual role assignments were not inspected. No vulnerability exploit was attempted.
- Existing tests were read, not rerun. Their presence is evidence of intended coverage, not a claim that this checkout's tests currently pass. Reviewed the README integration-test restrictions; this audit did not touch the disposable database or running application.
- Changed only this new report. Code, configuration, migrations, and tests were left untouched. Source references are repository-relative, one-based line references for this snapshot; recheck them after later edits.

### Administrator protection

`UserAdministrationService.cs:216-223,307-332` prevents removing/deactivating/deleting the last active directly assigned Administrator in sequential operations. `:290-298` rejects unidentified actors and self-deletion. **Confirmed limitation:** `actingUserId` is supplied by the caller and is never verified as the actual caller or an Administrator. The current Users page obtains it from `ICurrentUser`; no HTTP user-management API was found. **Requires Verification:** two administrators concurrently removing each other could both pass the count check; no serialized transaction or database invariant protects that count. The future invariant must include role/grant/inheritance edits that can eliminate administrative capability.

## 4. Complete Authorization Check Inventory

### Counting methodology

The inventory counts **documented gate sites**, not roles mentioned or lines matched by a search. A page attribute, opening `AuthorizeView`, guarded operation's authorization call site, explicit active-account/owner/membership decision, or data-access scope is one entry. Entries are deduplicated by **source file + source line**; multiple controls or clauses on the same line are grouped. The same helper invoked at different service entry points is counted separately because each invocation must be migrated. A helper implementation and its call sites are deliberately separate entries. Declarations, closing markup, exception handlers, DTO properties, formatting comparisons, test assertions, and role seeding are not counted as enforcement. Authentication checks, account safety/privacy conditions, lifecycle filters, and intentional anonymous/delegated entry boundaries are included and labeled. Business-only conditions are documented separately. Thus the total is broader than the number of hardcoded role checks and is not a count of independent permissions or vulnerabilities.

The tables are an implementation checklist, not a vulnerability count. A helper and its caller can both appear because they have different migration work. Candidate search matches are not automatically promoted to findings. Files with no authorization are in section 5's separate operation inventory. Ordinary HTTP business routes inheriting the single fallback policy are listed in section 9 but are not counted again as distinct explicit gate sites.

All references below are relative to `src/Confast.Web/`. Permission keys are recommendations; decisions marked open must be resolved before granting them.

## 6. Proposed Permission Catalog

**Recommendations, not implemented permissions.** Identifiers are stable PascalCase resource/action keys. Display labels and exact protected methods are included so the catalog is usable in constants, policies, persistence, and an editor. Type **Resource** means supported CRUD; **Action** means a named workflow/capability. **Baseline** adds an explicit trusted boundary where current normal UI has authentication alone; **Replace** maps an existing role/owner restriction; **Mixed** has both. Allowed roles describe current ordinary caller paths, not a proposed new seed policy.

Permission checks authorize the operation; workflow restrictions and conversation membership remain mandatory. Read permission is not automatically required for every write unless an explicit prerequisite convention is adopted. Do not let a save method accept sensitive field changes merely because its ordinary update permission is present: compare persisted values for deviation, receipt, departed-correction, and configuration changes.

## 10. Migration Risks and Compatibility Concerns

1. **Baseline access is broader than role labels imply.** Resolve R/no-role writes and Auth-sensitive inspection actions first. Compatibility and least privilege conflict here; do not pretend both can be preserved without a policy decision.
2. **Additive inheritance can broaden current asymmetries.** Q and P share tracking writes but differ on allocations/planning/logs/reports. A broad common parent can inadvertently grant both. Use explicit seed manifests and compare effective sets before cutover. There is no current deny role to reproduce.
3. **Role rename/deletion and qualification semantics.** Remove authorization dependencies on names, retain role IDs and Identity integration. Decide whether Quality inspector eligibility is a protected qualification, role, or other domain data; don't infer it from permission possession.
4. **No-role and inactive users.** Zero-role accounts have baseline access today. Disabled account checks remain mandatory even if grants are cached; unavailable permission data must deny protected work without silently treating it as baseline access.
5. **Session/cache freshness.** Version user assignment, role grants, and inheritance graph; invalidate descendant-role users when parents change. UI and HTTP/circuit/service decisions need consistent versions. A role-edit change affects many users without `UpdateUserAsync` running. Use bounded cache staleness deliberately; do not fit large effective permission sets into cookies by default.
6. **Administrator lockout.** Preserve a recovery-capable administrator under concurrent user, role, grant, and inheritance changes. Define whether an administrator means a protected role or effective recovery capability. An account that can read Users but cannot repair grants is not sufficient recovery coverage. An active administrator awaiting initial password setup also does not establish usable recovery access (F17); avoid treating temporary lockout as a permanent loss of that invariant without an explicit policy.
7. **Identity update atomicity.** Existing add/remove/stamp calls can partially succeed. New grants/graph/user changes need transaction/concurrency handling and clear audit records; confirm Identity store context/transaction ownership before composing operations.
8. **Private chat scope.** A union of app permissions cannot union conversation membership. Existing A channel metadata authority is scoped and owner/member behaviors differ. Role-editor access must not become private-history access through an omnipotent wildcard.
9. **Trusted renderer and delayed work.** Active-user guards on every service would reject renderer/worker. Conversely, broadly exempting any system principal would expand access. Authorize initiating operations and narrow delegated execution.
10. **Cross-module projections.** Inspection creation consumes parts/criteria/gages/user display names; receiving calls inspection creation; review consumes schedule snapshots; packages consume inspection/documents/plant templates. Avoid requiring full administration of dependencies or letting a lower-grant caller use an internal helper to escape its entry-point guard.
11. **Data-dependent exception actions.** Existing A departed correction bypass applies only to metadata/B/L and selected deletion. Update permission cannot bypass content/history locks. Sensitive save fields must have server-side diff checks.
12. **Read side effects.** Public-channel enrollment and scheduling catch-up occur on reads. Decide which are trusted domain maintenance and keep them explicit; don't equate all writes with user CRUD.
13. **Database migration.** Future role-permission and inheritance relations should be relational, unique, FK-constrained, transactionally changed; graph cycles must be rejected under concurrent changes. No schema/migration was created in this audit. Review existing Identity seeds, role-claim data, production role assignments, and bootstrap configuration in a separately authorized read-only environment inventory before writing migration.
14. **Auditability.** Record grants/role inheritance/assignment changes with actor, prior/new state, time, and revision; handle authorization-denied logs without exposing business data or secret render tokens. This is proposed behavior, not current implemented authorization audit history.

## 12. Recommended Implementation Sequence

3. Design minimal relational role grants and multi-parent inheritance; constraints, concurrent cycle prevention, atomic role/user edits, administrator survival, and migration preserving existing role IDs. Review before applying schema changes.
4. Implement effective grant evaluation and common service guard with actor/Active checks. Add test harness and graph/revocation/admin-safety tests before connecting live workflows.

## 13. Open Design Questions

1. Should R and zero-role users retain their current baseline writes, or should migration explicitly correct them? Which Auth inspection actions (delete, flip, lineage undo, deviation, send, temporary completion) were intentionally broad?
2. What confers administrative recovery status: a protected Administrator role, a designated capability set, or both? Can that role be renamed/deleted, and what protects the final administrator under concurrent graph/grant changes?
3. Are permission writes additive without prerequisites, or do writes require resource read? Define dependent lookup/projection access so package send/receiving/report users don't need user/settings administration or unrestricted reads.
4. Does `Chat.AdministerChannels` retain nonmember metadata/delete authority, and does it ever grant owner-management powers? Current code says metadata/delete yes, private-member management no, private-history read no.
5. Should every chat member keep channel duplication/shared ordering/folder-management/group invitations? Existing rules differ from owner-only channel metadata editing. Do queued personal drafts remain visible after removal?
6. When a user loses Send/Schedule permission, should already-queued messages fail at delivery? Recommendation: recheck at delivery; decide failure/retry/cancellation and user feedback.
7. What revocation latency is acceptable for active cookies/circuits/cached grants, and what consistency guarantee is required during concurrent mutation and revocation? Recommendation: next guarded operation checks current version; UI promptly refreshes or hides sensitive state.
8. How should qualified inspectors be identified when Quality roles become configurable/renameable? This is domain eligibility, not automatic permission inheritance.
9. Are scheduling settings/rates/global email CC values confidential or simply editable only by selected users? Existing normal schedule projections and send workflows read values behind admin-only editor pages.
10. Should schedule catch-up remain read-triggered or move into a dedicated maintenance worker? How are trusted internal identities composed and audited without a public bypass flag?
11. Should Development date control be admin-only and available only to authenticated callers? How is bootstrap configuration disabled after provisioning and prevented from restoring revoked grants?
12. Who may create/delete roles, edit grants, or change inheritance? Do these require separate control-plane capabilities, and how will escalation and recovery invariants apply to those edits? Those new operations are outside the existing-operation catalog.
