## Scheduled-message delegation and lifecycle

Each new instruction stores a server-generated unique operation/request UUID, fixed purpose, original sender/conversation/thread/reply/body, creation/due timestamps, installation generation, catalog version and originating authorization epoch. It never contains credentials, cookies or an effective-permission credential. The actor and version come from the single already-authorized submission operation. A PostgreSQL trigger prevents changes to the original intent/destination/sender and reopening terminal receipts; restrictive composite FKs bind thread/reply/delivered-message IDs to their conversation. No user API edits queued bodies or attachments.

A row progresses Pending → Delivered, Failed or Canceled. A failed row can be explicitly canceled by its sender to dismiss it. Successful delivery retains its message ID and completion timestamp in the same transaction as message/attachments/mentions/activity updates. Queue rows are no longer deleted on success. Canceled/completed rows are excluded from processing and the Scheduled inbox. Failures retain the original draft/attachments and safe diagnostic code/text; drafts are readable only by their sender with current Access and destination membership. No raw message body is copied to security history/log messages. Operator retention/storage policy for receipts remains deployment work; no automatic purge was invented.

The worker derives identity only from the selected locked database instruction. Its permission evaluation shares the delivery Repeatable Read transaction and uses the existing versioned engine. It requires current ScheduleMessages plus Access/SendMessages, Active account, Ready/catalog-valid installation and current membership/live destination/thread. Epoch changes cause fresh evaluation, not automatic invalidation of unrelated work. Generation or catalog changes invalidate the delegation. Password changes and security-stamp rotation invalidate old interactive sessions but do not cancel a persisted user instruction: the worker validates the current account stamp and current permissions. Deactivation, missing accounts, lost grants or membership deny permanently. Referenced user/thread hard deletion is normally prevented by restrictive FKs; if a sender cannot be resolved, evaluation denies. A soft-deleted conversation cannot receive content. A removed/deleted reply target preserves the existing policy of sending the scheduled text without its reply link.

SKIP LOCKED is attempt ownership: the row lock lasts for the transaction, so cancellation/competing workers serialize. Delivery and its terminal receipt are atomic; an ambiguous commit is resolved by re-reading the stored state, never by inserting another message. Successful/failed/canceled requests do not revive when grants return. Notifications follow commit and remain ID-only hints; lost process-local hints are repaired by existing normal reads/refresh.

## Retry and recovery

The delivery window ends seven days after the original scheduled time. Due requests inside this window catch up after an outage/restart; older requests become terminal Expired with their drafts retained. There is no arbitrary maximum scheduling horizon beyond supported timestamp arithmetic.

Each database-accessible attempt is recorded; up to five attempts are allowed. Transient failures roll back the entire delivery transaction, then a fresh transaction re-locks the request before recording retry ownership/state. Delays are 15, 30, 60 and 120 seconds. Unexpected per-request infrastructure failures share the bound; recognized permanent validation errors terminate immediately. Authorization/destination/generation failures are terminal, not retried. Current sender authority is rechecked on each retry. Cancellation or another worker's committed terminal receipt wins over a stale retry recorder.

If the database is completely inaccessible, an attempt cannot be durably recorded; no content commits and the hosted worker backs off from 10 seconds to five minutes. It resumes only database-backed decisions when service returns, and the fixed delivery deadline still applies. Each pass is bounded at 100 requests. The host's polling lifetime is intentionally continuous; individual messages cannot receive indefinite delivery attempts. Shutdown cancellation rolls back uncommitted work and leaves it recoverable. No user-facing retry notification system was added.

## Rendering review and compatibility

The existing Data Protection v2 purpose, inspection ID, two-minute expiry and protected rendering options remain. TimeProvider makes exact expiry testable. Issuance requires the live matching Export/BuildPackage operation; temporary completion independently requires TemporarilyCompletePackage and changes only the rendered model. A valid issued capability may finish after its initiating grant is revoked until expiry; it remains reusable within that narrow lifetime. No one-use or immediate-revocation behavior was introduced.

A concrete defect was corrected: a caller-supplied base URL/Host header could choose the destination for a render capability. The renderer now derives its callback origin from the server listener, or the operator's `InspectionRendering:ApplicationOrigin` setting for reverse-proxy deployments. Request authority is never used for the callback. Wildcard listener addresses map to local loopback. HTTPS certificate errors are no longer ignored. A new context has no human cookies and blocks service workers. The request policy allows only the exact URL/document and local static resources, blocking redirects/nested protected routes/external requests. Options/query are validated before launching. Print-capability responses use private no-store, nosniff and no-referrer. Playwright error text containing bearer URLs is not propagated into application logs/errors. Operators must also redact query tokens in proxy/request tracing and protect the persistent key ring.

Package building and email delivery remain separate, synchronous human operations. Building a package grants no email-send authority. The renderer never calls arbitrary public application services as Root. Temporary completion remains nonpersistent. No live email was sent during verification.

## Startup, diagnostics and operator boundaries

Normal startup no longer re-adds Administrator, reactivates BrowserTestUser, restores its roles, creates deleted role definitions, repairs role relationships or changes grants. Initial account provisioning is atomic and serialized, but never selects Root or rebuilds the security graph. Schema/catalog changes remain reviewed migrations, with existing manifest mismatches failing closed at protected operations. The existing offline Root procedure is unchanged; no provisioning/recovery route was added.

The Development SMTP route intentionally changes from a live Rackspace proof of concept to an email preparation diagnostic. It retains MIME/sender validation with a fixed invalid test recipient and in-memory transport. It cannot unintentionally read production SMTP credentials or send externally. Rackspace deliverability/header acceptance is no longer a web utility and was not claimed here. The global Development date affects many workflows, so its mutator now requires the existing Root-only security permission rather than granting calendar/write authority to all signed-in users.

Workers can share a least-privileged runtime role: queue SELECT/INSERT/UPDATE and existing chat/member/attachment tables, Identity/security graph SELECT, normal business DML and required sequence use; no schema alteration, trigger disabling, provisioning or owner authority is needed for worker authorization. Startup first-account creation additionally needs ordinary Identity DML, never owner DDL. Schema migrations, protected offline provisioning/recovery, receipt archival and destructive disposable-test reset belong to separate controlled operator credentials. The current local connection is owner-level; trigger tests are structural regression evidence, not protection against a compromised owner credential. No database roles/credentials/grants were changed. Production privilege split, restore rehearsal, shared keys, proxy origin, multiple instances and notification backplane/cutover remain Phase 3G.
