# Phase 3F Authorization Administration UI

Implemented October 16, 2026. This phase builds on the existing 164-key catalog, RoleGraph evaluator, AdministrativeAuthority delegation checks, security lock, transactional audit, and versioned cache. No catalog/seed, schema, migration, development Root, or development/production database changes are part of this phase. Phase 3G is not started.

## Roles Matrix And Editing

`/admin/roles` requires Roles.Read. The searchable role list includes descriptions, enabled/protected status, direct/effective permission counts, direct parents, and direct assignment counts. Protected status uses SystemRoleKind, never a name comparison. Root's 164 effective keys derive from designation; its direct-grant rows are empty and locked. ReadOnly's definition is protected and its membership remains optional.

PermissionMatrix uses PermissionCatalog.All, including the one protected Root-only key. Functional groups and category/search filters use catalog metadata; filtering does not replace the draft HashSet. Rows show direct selection, inherited operational grants, effective grants, prerequisite usability, granting roles, and editable/removal-only/locked explanations. There is no separate description field in the catalog: its display name, key, category, kind, and prerequisites provide the available purpose information without inventing definitions.

An effective permission is a grant in RoleGraph.EvaluateOrdinary's enabled union; usability additionally requires the catalog's expanded prerequisite set. It is still subject to private membership, ownership, account state, and business rules. Dormant stored sources are displayed separately and are not labeled effective. User matrices distinguish inactive accounts from their stored grants. User Direct Grant means a grant stored on a directly assigned role, not a grant stored on the account.

AdministrationProjection derives each operational source from RoleGraph's existing provenance. Stored sources come from its direct grants and structural closure. All granting roles are retained, including duplicate-path and multiple-anchor cases. Details list up to twelve inheritance paths per source and explicitly mark additional omitted paths. Each displayed path shows disabled branches; details separately show whether the granting role itself is enabled. This bound limits presentation only; it does not affect RoleGraph evaluation, sources, stored envelopes, or delegation validation. Provenance impact compares a deterministic fingerprint of the complete relevant graph, so changes beyond the first twelve displayed paths are still detected.

Direct grants, metadata, enabled state, and parent selections stay local until Save Changes. The page marks unsaved edits and allows saving directly; Preview Changes is optional. Deletion still requires a fresh permitted deletion preview and explicit confirmation. Inherited grants cannot be removed by a child checkbox; changing the corresponding direct source or parent relationship is explicit. A held unavailable key on a disabled lower role remains removable, with additions denied. A temporarily unchecked original grant can be restored as part of reverting the unsaved selection. All advisory controls remain subject to final server validation, including the full resulting stored envelope.

Root may create independent ordinary roles; other actors choose an enabled directly assigned administrative anchor. Creation remains empty and unassigned. Deletion shows direct assignment count, incident relationships, descendants and authorization effects, then requires confirmation. Assigned roles cannot be deleted. Incident edges are removed without reparenting.

The inheritance section explains child-to-parent direction, direct parents, all transitive ancestors (including grant-free roles), direct children and transitive descendants, disabled roles, and unavailable choices with reasons. Ordinary roles may select ReadOnly as a parent when the editor holds inheritance authority and every stored ReadOnly permission. ReadOnly remains protected against editing, deletion, or acquiring parents; inheriting it does not add editable management reach. Cycles, Root relationships, unauthorized parents, and unsafe reparenting are rejected on the server.

## Preview And Commit

RoleAdministrationService.GetEditorAsync returns role metadata, direct grants, parents, stamp, and epoch from one Repeatable Read snapshot. It does not combine stale list metadata with a newer editor concurrency token. PreviewAsync reads current state in another Repeatable Read transaction, checks the submitted epoch/stamp, and runs the same ValidateEditorChange/BuildSecurityGraph rules used by SaveEditorAsync. Existing SetGrants/SetParents methods share BuildSecurityGraph too.

A valid preview reports selected-role effective additions/removals, unchanged-effect provenance changes, newly unusable keys, stored-envelope additions/removals, descendant deltas (including disabled descendants), active assigned-user effective-change counts, actor deltas, aggregate management-reach changes, incident relationships, and the version used. Actor safety is checked independently per directly held anchor, including disabled anchors; union reach is only a display summary. Invalid proposals return a rejection and the committed matrix rather than fabricated partial results. Stale versions/stamps raise a recoverable conflict.

Changed-user counts account for each user's complete directly assigned role union. Root and inactive accounts are excluded from current effective-change counts. Roles.Read reveals only aggregate user impacts; no user identities, credentials, authentication stamps, or protected account details are returned in the preview. Generation and role ConcurrencyStamp identify the preview's installation/entity version; the Identity SecurityStamp is never projected.

SaveEditorAsync obtains AuthorizationMutationLock with the expected version before resolving current authority. It repeats all operation-specific permissions, strictly-lower/protected/delegation, graph, dormant-envelope, actor nonincrease and per-anchor checks. Metadata, grants, parent edges, audit details and final epoch commit together on the Identity DbContext. Removed edges are saved before inserts so transient graph states also remain acyclic. The preview is never an authorization capability and performs no writes or invalidation publication.

RoleEditDraft retains the original expected epoch/stamp after denial or conflict. Reload And Reapply reloads current state and reapplies only the local additions/removals and changed scalar fields. Unrelated committed edits survive. Reapplied edits may be saved directly or optionally previewed and can still be denied; Discard Changes explicitly replaces the draft. Switching roles with a dirty draft requires discard confirmation.

## User Administration

The existing Users layout remains. RoleCheckboxes exposes disabled assignments, eligibility and reasons, with Root/self restrictions still enforced by the service. UserEffectiveAccess offers Review Current Access and Preview Assignment Changes. Both use a trusted Users.Read boundary; assignment preview additionally requires Users.ManageRoles, the editor epoch/stamp, and AdministrativeAuthority.RequireAssignment. Matrix projections and deltas use AdministrationProjection and RoleGraph, including multiple directly assigned roles and dormant envelopes. The view contains no credentials, reset tokens, or security stamps. Root designation is explained separately.

Assignment-only edits no longer rotate Identity SecurityStamp. The existing epoch triggers revoke permissions on the next protected operation while the session remains valid. Metadata/security edits retain the existing stamp invalidation policy; credential/reset/deactivation protections are unchanged. This deliberately supersedes Phase 3C's assignment-only logout behavior. Password-reset issuers remain rechecked against their current permission, hierarchy and stored envelope at redemption.

UserEditRecovery supports explicit Reload And Reapply and Discard Changes, preserving role deltas and locally changed fields without replacing unrelated committed fields. Refresh no longer restores an intentionally unchecked ReadOnly creation choice. New-user default initialization still selects ReadOnly.

## Advisory Refresh

AuthorizationChangeNotifications is a process-local, payload-free invalidation event. Successful role/account mutations publish after commit. Subscriber failures are logged and isolated so a disconnected renderer cannot make an already committed edit appear to fail or block other subscribers. MainLayout marshals/coalesces hints onto the circuit renderer, reloads navigation permissions and increments a cascading AuthorizationRevision. PermissionComponentBase refreshes its advisory snapshot; an advisory-only parameter change invokes OnPermissionsChangedAsync and rerenders without rerunning page loading lifecycle methods. Duplicate unchanged parent/cascade deliveries also avoid reloading the model. This preserves open Customer/Part/Inspection/Receiving/Scheduling/Tracking editor models. Administration updates authority/choice projections without rebasing expected concurrency state. Chat reauthorizes normal reads or redacts protected content immediately on Access loss. Composer drafts retain the pre-existing recovery policy.

No AuthorizedOperation is retained in a component. Every subsequent protected service operation independently checks current primary-database account/version state. No global authorization polling loop or forced logout was added. Existing chat unread/presence refresh remains. Navigation and normal parameter loading continue to refresh advisory grants. Direct SQL/operator edits and changes on another process do not emit these process-local hints: their next protected operation still observes the database epoch; normal navigation/chat refresh also catches them. Distributed notification delivery and multi-instance deployment verification remain Phase 3G.

## Channel Moderation History

The channel header exposes Moderation History only with Chat.DeleteOthersMessages plus Chat.Access. ChatModerationHistoryView uses the existing ChatService.GetModerationHistoryAsync, which independently requires current channel membership even for Root. It shows the latest 200 records with moderator, original sender, UTC deletion time and reason; names use existing accessible chat user labels, falling back to historical IDs. It exposes no message body, attachment bytes, mutation, or global dashboard. Permission denial clears loaded records and refreshes chat advisory authority. Access loss removes the panel and protected content.

## Remaining Limits And Phase 3G

The matrix deliberately uses horizontally scrollable tables on narrow screens; the desktop role list stacks above the editor on tablets. Path display is bounded, user impact is aggregate, and permission usability cannot enumerate every contextual business rule. The full graph/epoch is rechecked on final commit. A large installation may eventually need additional batching/pagination for role and account impact projections; this phase adds no persistent projection tables or distributed architecture.

Physical iPad, multi-instance invalidation delivery, production runtime/operator database privilege separation, restore/recovery rehearsal, cutover, and rollback remain unverified deployment concerns for Phase 3G. No production-readiness claim is made and no cutover is initiated.
